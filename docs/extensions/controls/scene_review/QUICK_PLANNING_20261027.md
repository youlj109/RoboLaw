All nine latest visual-revision scenes received one MotionGen query each with
seed 42. Six returned trajectories; three returned `MotionGenStatus.GRAPH_FAIL`
and were skipped without retrying. These are **approach trajectories only**:
start to prepress (buttons) or pregrasp (temperature knob). No press, turn,
contact-feedback control, physical playback or data collection was performed.

## Scope And Budget

- Same original robot pose, original TCP target and fixed IK branch policy.
- Initial arm/gripper states come from the original matching physical baseline
  at the prepress/pregrasp phase, not a newly measured live simulation state.
- Source inspection stages provide nominal kitchen geometry; only the selected
  hazard is added from that scene's final visual-revision config.
- One fixed-branch IK solve and at most one `plan_single_js` call per scene.
  MotionGen uses `max_attempts=1`, graph seeding enabled, 15 s solver timeout,
  and normal internal collision/self-collision constraints. Its internal seed
  population is not nine repeated task attempts.
- A 100 s worker wall limit prevents unbounded loading/search. All nine reports
  recorded exactly one MotionGen call; no wall limit was reached.
- Standard speed retiming is applied to returned paths. This is not a collision,
  smoothness, contact, dynamics or execution validation.

At the user's request, no independent dense path/FCL clearance audit, safety
counterfactual, long-term stability test, task-success check or physical trial
was run. No safety threshold was disabled to make a query succeed. Output
`generated` means only the planner returned a path; `safety_validated` and
`task_success_validated` remain false. A one-shot failure does not prove the
scene or task has no solution.

A report-publication relative-path error after the first query was corrected;
resume reused its existing result, without querying that scene again. Cached
results are never regenerated by `--resume` when `result.json` already exists.

## Web Review

Open <http://127.0.0.1:8765> and refresh once to load the planning controls.
The page shows generation progress, per-scene status, raw result/log downloads,
an orbitable/scrubbable kinematic preview and editable manual notes. Arm lines
are joint-frame connections, not collision surfaces; orange/grey boxes are
display AABBs, not proof of actual contact or clearance. Failures show only the
start/target, with playback disabled.

Manual review categories and notes autosave with conflict protection. Marking a
candidate for retention does not mark it safe and does not trigger another run.
Failure hints propose alternative elbow postures, approach directions or waypoint
regions as **untried annotation candidates**, not verified repairs. Keep the
original task target and operation axis; do not silently relax collision margins.

## Reproduction

Use a fresh directory for a genuinely new batch. Existing failed queries are not
automatically retried. The following command only republishes/resumes run01 and
reuses its completed results:

```bash
env ARENA_CONTAINER=robolaw-arena python3 scripts/extensions/controls/quick_plan_batch.py --output reports/controls_planning_quick_20261027/run01 --resume
```

The server and viewer use the original scene-annotation database; visual-review
history and user scene notes were preserved. Planning annotations occupy
separate fields. No commit/push or old dataset/report replacement was performed.

Tool verification: 18 storage/HTTP tests passed. Actual Firefox desktop/mobile
tests passed trajectory scrubbing, playback, failed-scene start-only display,
manual planning-note/category autosave and reload recovery, image switching and
conflict handling. Tests used a scratch database, not the user's annotations.
UI captures: `data/planning_20261027_page_desktop.png` and
`data/planning_20261027_page_mobile.png`. Current annotations/history were
exported to `data/planning_only_20261027.json`; later edits remain in the live DB.
