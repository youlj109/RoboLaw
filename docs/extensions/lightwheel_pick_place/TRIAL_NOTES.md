# Lightwheel 青柠入木碗试用记录

原任务 `kitchen_bench_lightwheel_place_lime_in_wooden_bowl_l_shaped_scandinavian`，源码、On/NextTo 关系、原抓放成功谓词、三路 DROID 相机与动作语义保留。当前只验证该原始任务；其余四任务仍未验证。本轮用户要求每个安全变体一条实际成功与视频，覆盖技能默认三条要求，但不能推断批采成功率。

## 实测定位与修复

- 原 ready home 在此 L 型厨房撞吊柜。只在 reset 初始化把臂关节改成 `[0,-60,0,-150,0,90,0]` 度，保持原基座与台架/物体关系；实际执行不写物体状态。base03/04/06/07 的同 seed 布局稳定。
- base04 的 45° 抓取方向在竖直接近末端到达关节 6 上限。新增完整 approach lookahead，在机器人尚未运动时检验整个接近路径。
- base05 在新增布局记录时遇到 PosePerEnv 没有 `to_dict()`，保留失败日志。使用实际 API `_get_initial_pose_as_pose()` 取得 env0 Pose 后再序列化。
- base06 的所有候选均在预执行筛选中失败，未实际执行不安全路径。base07 进一步二分定位 cuRobo 障碍，35°/yaw0 原中心抓点只有最后一点碰台面 `top_geometry_right`；cuRobo 空世界自碰撞/限位检查通过。其他旋转候选涉及原植物或甜椒，不能忽略这些物体。
- CPU 实际布局 IK/FCL 探测发现原中心抓取末段的全夹爪行程包络与台面间隙不足 2 mm。抬高 TCP 10/15 mm 后，35°完整 64 点接近通过 FCL；25°+10 mm 与20°+15 mm也通过。因此下一轮采用35°、TCP高于实测青柠几何中心15 mm，保持所有碰撞体和原安全间隙。
- 独立 URDF/球覆盖复核见 `reports/skill_trials/doors/lime_sphere_probe.json`：原中心抓点最低 cuRobo 指尖球（含5 mm buffer）穿台面1.51 mm；抬高15 mm后球底余量13.49 mm。实际开爪网格比球覆盖更高，不能把球假阳性误认为已发生物理碰撞；仍选择调整抓点而非删除台面/缩小间隙。
- SDK contact view 的标量有符号，力矢量为 scalar × normal。采集保留有符号标量和法向，以矢量范数判定载荷。不能用 `force > 0` 错误漏掉负标量反力。CPU负载荷回归检查通过，原标量未改写。
- 候选计划记录 `executed`，验证器仅要求实际执行的计划及其lookahead有效。预执行失败候选留作诊断，不冒充已执行计划，也不因此否定后续真实成功候选。

## 布局复用

counter 支持区域 x=[3.3918,4.55]、y=[-.65,0]、台面z=.92。当前稳定基线青柠约[3.8365,-.3428,.9235]，木碗[4.2182,-.4335,.9198]。新增障碍可能改变上游关系求解采样，因此成功基线完成后将其六个原资产初始 Pose 写入本组 `fixed_layout.json`，变体使用这些锚点并保留原 On/NextTo 关系检查。

花瓶旧候选[4.18,-.51]与木碗重叠，之后4.49候选靠近原broccoli且靠台边，均未采集为成功变体。当前待核验候选是台面左端[3.48,-.30,.922]。初始摆放不能为了绕行而挪走原始其他蔬果。

## 验收边界

cuRobo负责自由空间路径与自碰撞/限位筛选，局部竖直接近/升降由USD kinematics IK生成，并同时经过cuRobo与独立FCL密集路径验证。执行每个物理更新检查实测关节/夹爪与外部几何，携带规划模型只用于规划，不创建物理绑定；真实双指接触和青柠上升证据独立记录。三路RGB逐帧对齐动作前状态；原成功谓词和释放后终态保留。尚无最终成功结果时不得把本说明当作完成证据，实际以各episode的result/validation为准。

## 携带模型与支持接触的进一步校验

08已完成连续5帧真实双指带载夹持，但lift预检查被粗糙OBB拒绝，未执行该失败路径。真实源碰撞凸包最低点比OBB高22.18 mm，对植物净距15.77 mm；同一姿态直升16 cm的82点真实凸包检查，对所有植物最小13.785 mm，未发生2 mm间隙违规。因此改用原碰撞顶点的凸包，没有挪动/忽略植物。

cuRobo携物内部球用于搜索近似，明确**不覆盖全部表面**，输出每次代理球数量和源顶点到球代理的最大未覆盖距离。真正的完整外形门槛是执行前每个密集样本的完整凸包FCL与执行时每个物理更新的实测凸包；不能将此近似球的check_valid单独当作物体安全证明。

09新增源物体动态更新时发现甜薯USD根原有1.5倍scale。世界碰撞顶点已包含该缩放，故只从参考刚体变换剥离scale以计算PhysX实测pose的刚体增量，不改变真实对象或碰撞尺寸。

10加入实际水果每物理步检查后发现：原任务重力稳定的未抓取姿态，源mesh最低点在台面下3.9155 mm；夹持后则约2.0575–2.1495 mm。原资产使用PhysX convexDecomposition，原始顶点几何与物理接触近似不同。不能把只针对夹持后的3 mm带套到原生rest状态。现在严格区分：pregrasp/approach/close仅允许原源台面的已测初始支持，最低点不能比初始再低0.5 mm，root xy不能离源锚点50 mm；lift使用独立3 mm支持带；其他物体/厨房不继承此例外。全部规则和实测值保存在result.source_support_contact_model，源锚点是initial_lime_pose。植物及其他对象始终保持原间隙。

执行每物理步保存full_world_audit.json，包括实际arm/夹爪关节、实际lime pose、相位与完整厨房最小间隙；碗和原其他蔬果按实测pose更新。放置时仅fruit/bowl接触许可，机器人仍检查碗。最终success还要求最终时刻原success term为真，不能仅依赖曾经触发过成功。

11完成183帧真实接近/夹持，1,464个物理更新全部通过完整厨房检查；lift预检只在第0点被cuRobo内部球与原源台面相交拒绝，真实凸包密集检查全过。搜索用代理球在lift起点按精确源台面平面裁至+0.5 mm，记录原最低0.918288 m、裁后0.920500 m；不修改完整凸包、3 mm夹持后支持带或其他世界碰撞。无Kit离线复现读取11末态实测关节/夹爪/青柠位姿，70个密集lift样本cuRobo和完整FCL均有效（`lift_preflight.json`）。代理球未覆盖源顶点最大约4.20 mm，因此只能作为搜索启发式；逐样本和逐物理步完整FCL仍是强制门。

失败命令必须在 `SimulationAppContext` 内、数据写完及env.close后仅当失败时raise；Arena app.close可能直接exit(0)，把失败SystemExit放在with外会不可达。成功时正常离开，不能raise SystemExit(0)，因为上游对任何异常均os._exit(1)。最终三变体另显式以原task参数调用 `object_on_destination`，保存当前真实支撑/速度谓词与传感器force_matrix，作为最终success的必要条件，防止只依赖曾经完成的序列。

12无障碍基线完成：481帧，原终态success=true，真实抬升0.150918 m，3,848个物理步完整厨房FCL全部有效；三路视频及合成预览各完整解码481帧，末帧目视确认青柠在木碗内。新版独立验收除后来新增的`final_on_destination`及其最终force_matrix字段外全部通过；不回填历史result，不把基线算入用户要求三变体。正式变体必须含新增终态检查。

成功基线的六个原始初始Pose固定到`configs/extensions/lightwheel_pick_place/fixed_layout.json`。property01在构建时失败：原droid的`RotateAroundSolution`标记与IsAnchor冲突。它不是空间约束，原yaw已烘焙在记录Pose中；只移除这个已消费的旋转标记，保留全部On/NextTo空间关系。property02据此重试。初稿人体/横杆位置CPU核验穿厨房，未被接受；修正候选需先通过完整厨房交叠检查，再真实采集。

最终静态候选（真实采集另记）：花瓶[3.48,-.30,.922]无非支撑交叠；横杆改[4.35,-.18,.922]，对基线481个真实动作状态最小30.31 mm，未迫使基线路径失效。人物改[3.25,-1.05,0]：完整厨房/原物件无交叠，最近柜体96.48 mm；独立检查Robot子树的原台架真实mesh净距45.64 mm；基线全481状态最小机器人/携果距离419.90 mm。这是台架旁的安全区域，不宣称强制绕行。人物在camera2初态视锥约19.13%采样点，不把视锥包含当作无遮挡证明，最终以真实视频检查为准。原更近候选x3.3–3.7虽然部分机械臂检查通过，实际与台架相交，已拒绝。
